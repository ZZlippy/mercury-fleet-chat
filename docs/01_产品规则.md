# Mercury Fleet MVP v1.1 产品规则

本文是当前 MVP 的业务规则说明。它用于回答“Mercury 正在解决什么问题”“系统中的对象是什么”“Operator 和车队分别做什么”。

## 1. 产品目标

Mercury Fleet 让 Operator 和本地集装箱拖车车队围绕同一张任务协作：

1. Operator 创建本地拖车订单；
2. 系统按已审核车队档案生成候选车队；
3. Operator 确认询价收件人；
4. 车队在任务对话中报价；
5. Operator 比较报价并手动选择车队；
6. 车队接单并更新整票运输节点；
7. 车队上传必需文件；
8. Operator 审核文件并完成订单。

聊天是主要交互入口，但 Order、RFQ、Quote、Booking、Shipment、Document 和 Fleet Profile 才是业务事实来源。聊天消息不能绕过业务校验直接修改状态。

## 2. 业务对象关系

```text
Order
  └─ RFQ（一个主记录，通过 revision 表示条件版本）
       ├─ RFQ Recipient（每个被询价车队一个）
       │    └─ Quote（保留多个历史版本）
       └─ Operator 选择一个有效 Quote
            └─ Booking
                 └─ Shipment
                      └─ Document 与审核结果
```

补充对象：

- Fleet Profile：车队的已审核能力档案及历史版本；
- Conversation / Task Context：车队与 Mercury 的聊天入口及每张任务的上下文；
- Exception Case：与正常流程并行的异常事项；
- Audit Log / Outbox Event：关键操作的审计和可靠事件投递。

### 2.1 为什么没有 Transport Leg

一张 Order 已经是一项能够独立询价、选择车队、执行和结案的本地拖车任务。起运国与目的国的本地拖车应分别创建两张 Order，海运仅作为两者之间的业务背景。第一版不再添加 Transport Leg 层级。

## 3. 两类订单

### 3.1 送港订单 `EXPORT_DRAYAGE`

正常流程：

1. 从指定堆场或提箱点提取全部空箱；
2. 把空箱运到仓库／工厂；
3. 完成全部集装箱装货；
4. 把装货后的全部重箱运往起运码头；
5. 将全部重箱交还码头；
6. 提交空箱提取证明和重箱交码头证明；
7. 等待 Operator 审核。

必填核心信息：服务国家、箱型、箱量、计划开始时间、装货地点、起运码头、空箱提取地点和空箱提取时间。

这里的正常“还箱”是将装货后的重箱交还码头。因取消、箱损等原因退回未装货空箱属于异常，不纳入正常状态链。

### 3.2 提港订单 `IMPORT_DRAYAGE`

正常流程：

1. 从目的码头提取全部重箱；
2. 运往仓库／工厂；
3. 完成送货和卸货；
4. 把全部空箱送到指定归还地点；
5. 提交 POD 和空箱归还证明；
6. 等待 Operator 审核。

必填核心信息：服务国家、箱型、箱量、计划开始时间、目的码头、送货地点和空箱归还地点。

### 3.3 不支持的订单类型

第一版不支持：

- 一张订单跨越两个国家；
- 起运国与目的国拖车自动组成父订单；
- 普通仓库到仓库的同国运输；
- 陆路跨境运输；
- 海运订舱或船期执行。

船公司、船名、航次、提单号和订舱号可以作为参考字段保存。

## 4. 多箱与承运规则

- `container_quantity` 必须是正整数，可以大于 1；
- 一张 Order 的全部箱量由一家车队承接；
- 一个 Order 最多有一个未取消的有效 Booking；
- 一个 Booking 最多对应一个 Shipment；
- Shipment 状态表示整张订单中全部集装箱的共同状态；
- 第一版不记录司机、车牌、车辆数量或单箱分配；
- 如果只有部分箱完成、缺箱或需要拆分运输，应联系 Operator 并创建异常，不能把整票状态误报为完成。

车队端在状态确认时必须理解为：

> 本状态适用于本订单全部 X 个集装箱。

## 5. RFQ 与报价

### 5.1 RFQ

一张 Order 最多有一个 RFQ 主记录。条件变化时增加 `revision`，不创建互不关联的新 RFQ。

每个收件车队都有独立 RFQ Recipient。不同车队不能看到彼此的收件状态、报价和聊天内容。

### 5.2 报价字段

Quote 包含：

- 金额；
- 币种；
- 是否全包；
- 是否能提供满足整票箱量的车辆能力；
- 最早可执行时间；
- 报价有效期；
- 条款；
- 基于哪个 Order version 和 RFQ revision；
- 当前状态。

未写币种时，当前规则解析器默认使用 USD，并在确认信息中明确提示。Operator 选择前仍应检查币种。

第一版不按历史表现、响应速度、准时率或推荐理由自动排名。Operator 查看报价业务字段后手动决定。

### 5.3 报价修改与历史

- 修改报价创建新记录，不覆盖旧记录；
- 旧报价保留，并通过替代关系与新报价关联；
- 过期、撤回或已失效报价不能被选择；
- Operator 选择报价时再次检查 Order version、RFQ revision 和 Quote 状态。

### 5.4 订单变更

RFQ 发出后，只要 Operator 修改车队可见条件，系统必须：

1. 增加 Order version；
2. 增加 RFQ revision；
3. 失效但保留旧报价；
4. 失效旧编号选择；
5. 向相关车队发送变更内容；
6. 要求车队选择“价格不变”“修改报价”“无法承运”或“稍后回复”；
7. 记录审计历史。

Booking 创建后的关键变更不能静默改写已经确认的 Booking，应转由 Operator 人工处理。

## 6. 车队档案与候选匹配

### 6.1 车队填写的字段

- 车队名称；
- 当前是否接单；
- 营运国家；
- 是否具备危险品运输能力；
- 是否具备冷藏箱运输能力；
- 联系人；
- 联系电话；
- 备注。

### 6.2 审核规则

- 车队提交能力信息后形成不可覆盖的档案版本；
- Operator 可以批准或退回；
- 审核期间继续使用上一份已批准档案；
- 新版本批准后才替换当前匹配依据；
- “正在接单／暂停接单”开关立即生效，不需要等待档案审核；
- Operator 还可以把车队系统账号设为启用或暂停。

### 6.3 候选车队规则

默认候选需要同时满足：

1. 车队组织账号处于启用状态；
2. 车队当前正在接单；
3. 存在已审核通过的档案；
4. 档案营运国家包含订单的服务国家；
5. 危险品订单要求车队具备危险品能力；
6. 冷藏箱订单要求车队具备冷藏箱能力。

系统显示匹配和不匹配原因。Operator 在发送 RFQ 前确认最终名单，并可以手动加入仍启用且正在接单的非默认候选；暂停接单或系统账号已暂停的车队不可发送。

## 7. 车队聊天与编号选择

### 7.1 任务级对话

车队可以在同一工作区看到多个任务，但每条消息、待回答问题和编号菜单都必须关联到明确任务。一个任务中的 `1` 不能误操作另一个任务。

界面显示 Order、RFQ、Booking 等业务编号，草稿、未读数和消息历史也按任务隔离。

### 7.2 不使用业务选择按钮

报价、接单和运输节点确认以普通文本显示，例如：

```text
请选择：

1. 我要报价
2. 无法承运
3. 稍后回复

请回复 1 / 2 / 3 选择。
```

车队通过输入框回复数字。Web、WhatsApp 和微信适配层都使用同一编号文本原则。

登录、任务切换、上传文件、档案提交等普通网页控件不是业务决策按钮，可以保留。

### 7.3 数字回复的安全规则

- 只在同一任务的最新有效菜单中解释数字；
- 没有有效菜单时提示用户查看最新消息；
- 超出范围的数字不改变任何业务状态；
- 已消费、过期或因版本变化失效的选项不能重复执行；
- 当系统正在等待报价金额时，`220` 应理解为金额，而不是菜单编号；
- 所有重要动作具备幂等和版本校验。

## 8. Booking

Operator 选择有效报价后创建 Booking，并向该车队发出任务。

Booking 保存选定报价、车队、确认金额／币种／条款、订单版本、订单类型、箱型、箱量和计划开始时间的快照。

Booking 不保存司机、车牌和具体车辆安排。

车队收到的主要选项为：

```text
1. 接受任务
2. 无法承运
3. 联系运营
```

车队接受后创建 Shipment，并从对应订单类型的初始状态开始。

## 9. Shipment 状态

车队只能按相邻业务节点前进，不能倒退或跳过关键空箱步骤。`DOCUMENTS_SUBMITTED`、`REVIEW_PENDING` 和 `COMPLETED` 由文件审核流程控制，不能由车队直接设置。

### 9.1 送港 `EXPORT_DRAYAGE`

| 顺序 | 内部状态 | 中文含义 | 更新者 |
| ---: | --- | --- | --- |
| 1 | `WAITING_EMPTY_CONTAINER_RELEASE` | 等待提取空箱 | 系统初始状态 |
| 2 | `EMPTY_CONTAINER_PICKED_UP` | 全部空箱已提取 | 车队确认 |
| 3 | `AT_LOADING_LOCATION` | 已到达装货地点 | 车队确认 |
| 4 | `LOADED` | 全部集装箱已装货 | 车队确认 |
| 5 | `EN_ROUTE_TO_TERMINAL` | 前往码头 | 车队确认 |
| 6 | `LADEN_CONTAINERS_RETURNED_TO_TERMINAL` | 全部重箱已还至码头 | 车队确认 |
| 7 | `DOCUMENTS_SUBMITTED` | 必需文件已提交 | 系统 |
| 8 | `REVIEW_PENDING` | 等待运营审核 | 系统 |
| 9 | `COMPLETED` | 已完成 | Operator 审核触发 |

### 9.2 提港 `IMPORT_DRAYAGE`

| 顺序 | 内部状态 | 中文含义 | 更新者 |
| ---: | --- | --- | --- |
| 1 | `WAITING_PORT_RELEASE` | 等待码头放箱／提箱 | 系统初始状态 |
| 2 | `CONTAINER_PICKED_UP` | 全部重箱已从码头提取 | 车队确认 |
| 3 | `IN_TRANSIT_TO_DELIVERY` | 前往送货地点 | 车队确认 |
| 4 | `DELIVERED` | 全部集装箱已送达 | 车队确认 |
| 5 | `EMPTY_RETURN_PENDING` | 等待归还空箱 | 车队确认 |
| 6 | `EMPTY_RETURNED` | 全部空箱已归还 | 车队确认 |
| 7 | `DOCUMENTS_SUBMITTED` | 必需文件已提交 | 系统 |
| 8 | `REVIEW_PENDING` | 等待运营审核 | 系统 |
| 9 | `COMPLETED` | 已完成 | Operator 审核触发 |

旧数据库中的司机分配或旧 Shipment 状态仅为迁移兼容，v1.1 新流程不会创建这些状态。

## 10. 文件与完成条件

送港必需文件：

- 空箱提取或放箱证明 `EMPTY_CONTAINER_RELEASE`；
- 重箱交还码头证明 `TERMINAL_HANDOVER`。

提港必需文件：

- 送货签收证明 `POD`；
- 空箱归还证明 `EMPTY_CONTAINER_RETURN`。

当前允许 PNG、JPEG、WebP、HEIC 和 PDF，单个文件最大 10 MB。

车队可以先上传文件，也可以到达最后一个运输节点后上传。只有最后业务节点和两类必需文件都齐全，Shipment 才进入待审核。Operator 可以：

- 审核通过：同一确定性操作完成 Shipment、Booking 和 Order；
- 退回：保留原文件和退回记录，车队补充或重新上传后再次审核。

## 11. 异常、审计与权限

- 异常事项与正常状态并行存在，不应靠删除历史解决；
- 关键操作记录操作者、对象、时间、前后值和原因；
- Fleet 与 Operator 使用不同登录入口和独立 Cookie；
- Fleet 只能访问本车队任务、消息和文件；
- Operator 才能审核档案、选择报价、停用车队账号和完成文件审核；
- AI 解析器只生成意图建议，最终仍通过确定性服务、事务和状态机校验。

## 12. 第一版验收底线

至少应能稳定演示：

1. Operator 创建送港或提港多箱订单；
2. 系统生成候选，Operator 确认收件车队；
3. Fleet 用数字和文本完成报价；
4. Operator 查看完整报价字段并手动选车队；
5. Fleet 用编号接受任务；
6. Fleet 依次更新整票状态，不能跳过空箱节点；
7. Fleet 上传两类必需文件；
8. Operator 退回或批准文件；
9. 批准后 Order、Booking、Shipment 同步完成；
10. 修改已询价订单时，旧报价和旧编号选项失效但历史仍可追踪。
