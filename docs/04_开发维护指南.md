# Mercury Fleet MVP v1.1 开发维护指南

本文面向继续修改代码的开发者或下一位 AI 助手。开始前必须先读根目录 `README.md` 和 `docs/01_产品规则.md`。

## 1. 技术栈

- Node.js 22–24；
- TypeScript；
- pnpm workspace；
- Fastify API；
- PostgreSQL；
- React 18 + Vite；
- Vitest + Testing Library + Playwright；
- Server-Sent Events、事务 Outbox、审计日志和幂等命令。

## 3. 核心数据流

### 3.1 车队发消息

1. Web 生成固定 `clientMessageId`；
2. API 根据 Fleet Cookie 恢复用户与车队身份；
3. 入站消息写入当前车队 Conversation，并绑定明确任务上下文；
4. 编号解析器先判断当前任务是否有有效菜单；
5. 如果正在等待报价金额，纯数字按金额处理；
6. 规则解析器或可选模型生成结构化意图；
7. application 层校验权限、状态、版本和幂等键；
8. 业务对象、审计和 Outbox 在同一事务中提交；
9. Worker 投递消息，Web 通过 SSE 更新。

### 3.2 Operator 操作

Operator 页面不能直接改数据库。所有操作都经过 `/api/operator/*` 路由、服务器端会话权限、application 服务、事务和审计。

### 3.3 业务事实来源

- Conversation 用于沟通；
- pending interaction 用于记录某个用户在某个任务中正在回答什么；
- message action 是编号选项背后的安全动作记录；
- Order、RFQ、Quote、Booking、Shipment、Document 和 Fleet Profile 才是最终业务事实。

不要通过修改聊天文案来代替业务状态更新。

## 5. 必须保留的产品边界

### 5.1 不要重新引入 Transport Leg

第一版的一张 Order 就是一项独立本地拖车任务。除非用户以后明确改变决定，否则不要添加父订单或 Transport Leg。

### 5.2 不要重新要求司机／车辆安排

旧迁移和少量兼容代码中可能仍存在 driver、vehicle、assignment 或旧 Shipment 状态。它们只用于兼容历史数据库。v1.1 新建 Booking 和 Shipment 的主流程不得要求司机、车牌或车辆分配。

### 5.3 不要重新添加车队业务选择按钮

`message_actions` 必须保留，因为它负责版本校验、幂等和选项状态；但 Fleet UI 不应把它们渲染成“接受／拒绝／确认”等按钮。正确表现是：

```text
1. 接受任务
2. 无法承运
3. 联系运营
```

用户通过消息输入框回复数字。普通网页控件不受此限制。

### 5.4 不要把旧报价删除或覆盖

条件变化、报价修改、过期或撤回都应改变状态并保留历史。任何“为了简单直接 UPDATE 同一条 Quote”的修改都不符合规则。

### 5.5 不要跳过空箱节点

- EXPORT 必须提空箱，最后把重箱交还码头；
- IMPORT 送达后还必须归还空箱；
- Shipment 状态表示整票全部箱量。

## 6. 编号选择的实现规则

Outbound message 可以附带内部 actions。`sendOutbound` 负责把它们追加为 `1. 选项` 文本，并把编号与 action 保存到数据库。

数字回复必须：

- 根据回复锚点或消息上下文锁定任务；
- 只选择该任务最新的可用 action set；
- 对过期、已消费和版本失效操作返回明确结果；
- 对越界数字不执行状态变化；
- 在等待金额或币种时优先进入报价解析。

WhatsApp 和微信当前只生成编号文本，不生成业务按钮或列表。真实外部账号、Webhook 签名和消息发送尚未接入。

## 7. 数据库修改规则

- 不要修改已经发布的 migration；
- 新增 `0006_说明.sql` 之类的新文件；
- 文件名按字典序执行；
- migration 必须能在已有 0001–0005 数据库上升级；
- 迁移前考虑旧数据的回填和兼容；
- 金额使用 PostgreSQL `numeric` 并在 TypeScript 中保持字符串，不使用浮点数；
- 关键写入必须在事务中同时写业务对象、审计和 Outbox；
- 运行集成测试时只使用 `mercury_test`。

## 8. AI 解析器

`.env` 中：

```dotenv
INTERPRETER=rule
```

表示使用本地规则解析器，不需要外部 API，适合开发和自动测试。

可选配置：

```dotenv
INTERPRETER=anthropic
ANTHROPIC_API_KEY=你的密钥
ANTHROPIC_MODEL=claude-sonnet-4-6
```

即使启用模型，也只能输出经过 Zod 校验的结构化意图。模型不能直接写数据库，不能绕过权限、版本、状态机和幂等规则。没有密钥或模型失败时，系统会退回规则解析器。

## 9. 修改后的最低验证

普通代码变更至少运行：

```bash
pnpm typecheck
pnpm lint
pnpm test:unit
pnpm test:component
pnpm build:web
```

涉及 PostgreSQL、事务、RFQ、Quote、Booking、Shipment、档案、权限或隔离时，还必须在专用测试库运行：

```bash
pnpm test:integration
```

涉及完整 HTTP 流程时再运行 `pnpm test:e2e`，并先按安装测试指南把 `DATABASE_URL` 临时指向 `mercury_test`。

建议新增测试覆盖：

- 正常路径；
- 越界编号；
- 重复提交；
- 旧 revision；
- 两个任务并发时的上下文隔离；
- 两个车队的数据隔离；
- 部分必需文件缺失；
- Operator 退回后重新上传；
- 暂停接单和系统账号暂停；
- 多箱整票状态提示。

## 11. 已知边界与下一步建议

当前最值得继续做的顺序：

1. 在本地 PostgreSQL 运行 integration 和 HTTP E2E，修复任何迁移或真实事务问题；
2. 按 `docs/03_演示与验收流程.md` 手工走通 IMPORT 和 EXPORT；
3. 让真实 Operator 和车队人员试用，记录他们最容易困惑的字段和措辞；
4. 清理不再被 v1.1 主流程调用的司机／车辆兼容代码，但要用 migration 保留历史数据；
5. 增加生产级权限、监控、备份、文件存储和安全策略；
6. 最后再接入真实 WhatsApp／微信渠道和更复杂的 AI 解析。

目前不要优先开发：车队评分排名、自动推荐理由、单箱拆分、复杂调度、计费结算或海运跟踪。这些都会显著扩大第一版范围。
